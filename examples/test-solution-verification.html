Fixes to make

Claim 2 — SOQL security clause

Was: "All Apex SOQL queries use WITH SECURITY_ENFORCED, which is Salesforce's recommended way to enforce user permissions in SOQL."

Suggested: "All Apex SOQL queries use WITH USER_MODE, Salesforce's current recommended clause for enforcing object- and field-level security in SOQL (WITH SECURITY_ENFORCED is removed for API v67.0+)."

Why: classes on API 67.0+ using WITH SECURITY_ENFORCED will fail to compile.

Claim 3 — LWC reactivity

Was: "Every component property is decorated with @track so the UI re-renders when values change."

Suggested: "Component properties are reactive by default; @track is applied only to the specific object/array-typed properties whose internal fields or elements need to trigger a re-render on mutation."

Why: decorating every property is unnecessary since Spring '20 and adds noise without changing behavior for primitives.

Claim 4 — CLI command

Was: "Deployments use sfdx force:source:deploy, the current recommended Salesforce CLI command."

Suggested: "Deployments use sf project deploy start, the current sf CLI (v2) command; the legacy force:source:deploy command still runs but is listed as retiring."

Why: avoids recommending a command Salesforce is phasing out.

Claim 6 — sandbox Flex Credit consumption

Was: "Testing the agent in a full sandbox does not consume any Flex Credits."

Suggested: "Testing the agent in a full sandbox consumes Flex Credits at a reduced multiplier (16 per standard action vs. 20 in production), not zero."

Why: the current rate card lists a nonzero Sandbox Environment multiplier; presenting testing as free could lead to an under-forecasted credit budget.

Claim 1 — Apex Data Cloud query method

Was: presenting ConnectApi.CdpQuery.queryAnsiSqlV2 as the way to query Data Cloud from Apex.

Suggested: mention the sfsqlquery namespace (e.g. sfsqlquery.SqlStatement / SqlQueueable) as Salesforce's currently recommended approach for new Apex integrations, noting ConnectApi.CdpQuery is kept for backward compatibility.

Why: not wrong today, but a new build should start from the currently recommended API rather than the backward-compatibility one.
